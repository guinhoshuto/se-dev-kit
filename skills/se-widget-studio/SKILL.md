# SE Widget Studio

Operate the shared Studio instead of building a widget-specific preview runtime. Resolve all referenced files relative to this `SKILL.md`. `<skill>` is the real path of its directory, not the link agents load it through (`~/.claude/skills/se-widget-studio`, where `../..` is `~/.claude`, since `node` and `cd` drop the `..` from the text): the Studio checkout, `<checkout>`, is what `realpath <skill>/../..` prints.

Read a reference by section, never whole when it is large (`studio-workflow.md` is about 23 KB and `catalog-authoring.md` about 16 KB): every link below names the section the task needs. List a file's headings with `grep -n '^#' <file>`, then print its lead (the lines before its first `##`, which define names such as `SKILL_DIR`) and the section, from its heading to the line before the next heading of the same level, with `sed -n '<start>,<end>p' <file>`. A link to a file's title means the whole file, and only small files get one.

## Choose the mode

- Use the **local Studio** by default for every widget task: upload, editing links, saved projects, previews, smoke tests, screenshots, videos, and marketing assets. It is the Studio web app running on this machine at `http://127.0.0.1:4310`, driven by `scripts/studio-client.mjs`. Before the first import, read [Start the local Studio](references/studio-workflow.md#start-the-local-studio), [Import a production widget](references/studio-workflow.md#import-a-production-widget), and its limits, [Boundaries](references/studio-workflow.md#boundaries); read the other sections of that file when the task reaches them: [Open and manipulate](references/studio-workflow.md#open-and-manipulate), [Test and render](references/studio-workflow.md#test-and-render), [Plan a large batch](references/studio-workflow.md#plan-a-large-batch), and [Known gaps](references/studio-workflow.md#known-gaps).
- The **hosted deployment** (`https://se-dev-kit.vercel.app`) is paused: its storage is suspended and it is not maintained. Use it only when the user explicitly asks, with `--origin`, and read the hosted section of [references/studio-workflow.md](references/studio-workflow.md#hosted-deployment-paused) first.
- Use the **local CLI** to develop or debug SE Widget Studio itself, or when a render must keep all of its PNG frames (`--keep-frames`, for a loop cut at frame 0 or a re-encode; posters and stills come from `outputs.video.stills` in any render) and the widget needs no Google Fonts, which the CLI blocks. Read [Invoke the CLI](references/local-workflow.md#invoke-the-cli) and [Commands](references/local-workflow.md#commands) in `references/local-workflow.md`, and [Develop SE Widget Studio itself](references/local-workflow.md#develop-se-widget-studio-itself) before changing the Studio. Before `init` in a widget repository, read [Invoke the CLI](references/local-workflow.md#invoke-the-cli).
- When themes, fixtures, scenes, scenarios, recipes, crop, camera, matrix variants, or video settings must be created or changed, read [Layers](references/catalog-authoring.md#layers) and [Compact example](references/catalog-authoring.md#compact-example) in `references/catalog-authoring.md`, plus [Field changes](references/catalog-authoring.md#field-changes) for a scenario or tutorial that changes fields, [Theme files](references/catalog-authoring.md#theme-files) for a theme, and [Widget media files](references/catalog-authoring.md#widget-media-files) or [Studio assets](references/catalog-authoring.md#studio-assets) for media the widget brings.
- Before authoring or rendering a tutorial video (`"mode": "tutorial"`), a "how to configure" walkthrough of the widget in a replica of the StreamElements overlay editor, read [Recipe](references/tutorial-video.md#recipe), [Steps](references/tutorial-video.md#steps), and [Duration](references/tutorial-video.md#duration) in `references/tutorial-video.md`; [Layout](references/tutorial-video.md#layout) and [Auto zoom](references/tutorial-video.md#auto-zoom) when the framing changes.
- To move the overlay behind a sold widget's StreamElements link (the product's overlay, in the real StreamElements overlay editor) to a new commit, read [references/se-editor-update.md](references/se-editor-update.md#update-a-sold-widgets-overlay) (8 KB, whole) and paste its versioned page scripts from `scripts/`; never retype them.
- Read [references/known-limits.md](references/known-limits.md#known-limits) (6 KB, whole) before planning marketing media, and, when the media is for a store listing, [Before rendering](references/marketing-assets.md#before-rendering), [Framing](references/marketing-assets.md#framing), [Stills](references/marketing-assets.md#stills), and [Review](references/marketing-assets.md#review) in `references/marketing-assets.md`. A listing cover video starts from the model recipe `examples/basic-chat/recipes/listing-loop-video.json` (one scene, one 15-second MP4, one job) and is cut to an exact loop with `scripts/cut-loop.mjs`, `--period <ms>` for a widget that repeats on uneven changes, and `--period <ms> --beat <frames>` for one that never holds still but changes on a fixed beat ([Loops](references/marketing-assets.md#loops)).

## Preserve the source contract

- Inspect repository instructions and the working tree before reading or changing a consumer widget.
- Treat production HTML, CSS, JavaScript, and FIELDS as source. Never rewrite or copy them merely to make Studio work.
- Put Studio-only behavior in JSON catalogs or the consumer's existing versioned Studio configuration.
- After a change to a widget's FIELDS or themes, run the CLI's `validate` on it (`node <checkout>/dist/cli/index.js validate <widget-root>`, `<checkout>` being what `realpath <skill>/../..` prints), in Studio mode too, and fix every error before testing: a button label over 24 characters pushes the StreamElements editor's field panel out of place, and a theme that ships sets every FIELDS key ([Theme files](references/catalog-authoring.md#theme-files)).
- For a new widget, once its FIELDS is written, run the CLI's `validate` on it and show the owner the field list it prints (the count by type, then each field's id, type, and label) before its first build or Studio run, and wait for their answer: the owner sets the field budget from that list, since the curve text widget reached 77 fields before anyone counted them. `validate` needs all four widget files, but the HTML, CSS, and JavaScript may still be empty.
- Keep `fieldData` separate from background, viewport, output size, camera, crop, and device scale.
- For test media, use the Studio's built-in sample images (`sws-sample:` references listed in [references/catalog-authoring.md](references/catalog-authoring.md#sample-media)) instead of generating, downloading, or uploading images, and never copy them into the widget. The client refuses them before any change when the selected Studio does not serve them; then stop and tell the user the Studio must be updated, rather than working around it.
- Use only synthetic, public-safe channel data, identities, messages, and events. Never submit StreamElements tokens, cookies, webhooks, private messages, or viewer data.

## Studio operation rules

Use `scripts/studio-client.mjs`; it defaults to the local Studio, `http://127.0.0.1:4310`, and accepts `--origin` (or `SE_WIDGET_STUDIO_URL`) for another Studio.

- The local Studio runs from the Studio checkout this skill belongs to (`<checkout>`, what `realpath <skill>/../..` prints), on `main`. If the client answers `No Studio is running at …`, start it as [references/studio-workflow.md](references/studio-workflow.md#start-the-local-studio) describes, then run the command again. Stop only a server you started, when the task ends, and only once `studio-client.mjs active` prints `"activeJobs":0`: every session uses the server on that port, and a local job runs inside it, so stopping it kills the jobs of other sessions too.
- Project capabilities and signed URLs are secrets. Keep access bundles mode `0600`; never print, quote, attach, commit, or paste their contents.
- Never `cat`, `jq`, or otherwise print the access files (`~/.se-widget-studio/access-*.json`), not even with secret-looking fields removed: their `editorUrl` carries the project key. List them with `studio-client.mjs projects`, which gives each file's project ID, origin, creation time, and project name; inspect one with `status --access <file>`.
- A `blocked` import already created the project and prints its diagnostics. Fix them with `pull`/`push` on that project; never import again.
- `pull` produces a capability-free draft with an opaque `etag`. Edit the complete `snapshot`, then `push`. A conflict must stop for reconciliation; never refetch and overwrite silently.
- `run` requires a new output directory, polls one accepted job on its own route, downloads authorized artifacts, and verifies byte counts and SHA-256. Show a render job's media with the CLI's `review` over that output directory, never with a board script of your own ([Test and render](references/studio-workflow.md#test-and-render)).
- A local job is a heavy render: it waits for the machine-wide render slot and then for the machine check, as the CLI does, and is refused by the disk guard when its frames would not fit. Run one job at a time.
- Open the private editor only when the user requests it, using `open-editor`; do not expose the fragment URL in a response or tool argument. If `open-editor` fails, stop and report its error: never assemble the URL yourself, and never open it through a browser automation tool, whose results repeat the address.
- Google Fonts work as in StreamElements, in preview and in jobs (see "Fonts" in [references/studio-workflow.md](references/studio-workflow.md#fonts)); never vendor fonts or edit the widget for them. Other runtime network requests stay blocked.
- Do not retry a mutation automatically after an uncertain response. Resume or inspect the accepted project or job instead.

## Local CLI rules

Invoke a pinned CLI, never an unpinned remote package: the consumer's locked dependency through `npm exec -- se-widget-studio` when the widget declares it, or a reviewed Studio checkout prepared with `npm ci && npm run build:engine` and run as `node <checkout>/dist/cli/index.js` on Node 24 (local captures and renders refuse a Node.js outside `engines`). Check current `--help`, then run `doctor` and `validate` before browser/media work. Dry-run recipe matrices before rendering and report their frame, file, and disk estimates. Never install a browser, FFmpeg, codecs, or fonts without explicit authorization. Require `--force` before replacing exact outputs, and never recursively clean a consumer directory.

## Completion evidence

Report the Studio origin, the project ID, and the private access-file path, never its capability. For edits, report the new immutable revision. For jobs, report terminal status, exact local artifact paths, byte counts, hashes, and media validation. Check anything on screen for less than 1 s (a fade, a flash, an entrance) frame by frame: decode every frame of its window from the video and measure each against a reference frame (the rest before it), never stills, which skip what happens between them. Video frames sample CSS transitions and animations at their timestamps, so a fade that comes out as a cut is in the widget: a CSS animation whose fill (`both`, `forwards`) holds the same property keeps Chrome from starting the transition, and `element.getAnimations()` right after the change lists no `CSSTransition` for it (se-wheel's `!results` exit, 2026-10-20). Keep Studio simulation separate from real StreamElements and OBS validation. When a task also tests in real StreamElements: after a FIELDS change, check the overlay editor's field panel for overflow (its `scrollWidth` greater than its `clientWidth`); report every visual anomaly, even when the feature under test works, since a test with an anomaly did not pass; say so before each Save; check a saved change by navigating the tab you edited to its editor URL again, never with `force` (a navigation the page holds back means unsaved changes: stop); and close every editor tab you opened, one at a time.
